Módulo de Inventario
Pizza Yaja ERP

Diseño e implementación del sistema de control de inventario, movimientos de stock y descuento automático de ingredientes mediante recetas de producción.

Sistema: Pizza Yaja ERP Tecnología: PHP · MySQL · PDO · AJAX Entorno: XAMPP localhost:3307 Fecha: Julio 2026
01

Descripción General del Módulo

El módulo de inventario es la capa de gestión de recursos físicos del ERP de Pizza Yaja. Su función central es mantener un registro preciso del stock de ingredientes, registrar cada movimiento que afecte ese stock y, lo más importante, conectar ese stock con las órdenes de venta mediante un sistema de recetas que descuenta ingredientes de forma automática cuando se completa una orden.

El módulo fue diseñado sin frameworks externos — toda la lógica corre en PHP puro del lado del servidor y se comunica con el navegador a través de AJAX con fetch API y respuestas en JSON, lo que permite actualizaciones en tiempo real sin recargar la página.

El módulo abarca tres archivos principales y se integra de forma transversal con el flujo de ventas:

  • erp/inventario.php — Interfaz principal: CRUD de ingredientes, movimientos, visualización de stock
  • erp/productos.php — Gestión de recetas por producto
  • descontar_ingredientes_fn.php — Función compartida que ejecuta el descuento automático

04

Migraciones Automáticas de Base de Datos

Una decisión técnica clave del módulo es que nunca requiere ejecutar SQL manualmente. Cada vez que se carga la página, el sistema verifica y crea las tablas necesarias si no existen. Esto se logra con dos patrones combinados:

Patrón 1 — CREATE TABLE IF NOT EXISTS: crea la tabla completa la primera vez; en cargas posteriores la instrucción se ignora sin generar error.

$conn->exec("
  CREATE TABLE IF NOT EXISTS ingredientes (
    id             INT AUTO_INCREMENT PRIMARY KEY,
    nombre         VARCHAR(100) NOT NULL,
    categoria      VARCHAR(50)  NOT NULL DEFAULT 'otros',
    unidad         VARCHAR(20)  NOT NULL DEFAULT 'unidades',
    stock_actual   DECIMAL(10,2) NOT NULL DEFAULT 0,
    stock_minimo   DECIMAL(10,2) NOT NULL DEFAULT 0,
    costo_unitario DECIMAL(10,2) NOT NULL DEFAULT 0,
    activo         TINYINT(1) NOT NULL DEFAULT 1,
    created_at     TIMESTAMP DEFAULT CURRENT_TIMESTAMP
  )");

Patrón 2 — ALTER TABLE en bloque try/catch: permite agregar columnas nuevas a tablas ya existentes (instalaciones previas del sistema), sin fallar si la columna ya existe.

// Agregar columna si faltaba en instalaciones previas
try {
    $conn->exec("ALTER TABLE ingredientes
                  ADD COLUMN categoria VARCHAR(50) NOT NULL DEFAULT 'otros'");
} catch(PDOException $e) {} // columna ya existe → se ignora silenciosamente
Por qué importa Este patrón resuelve el problema clásico de despliegue: si la base de datos ya tiene datos de una versión anterior del sistema, el script no falla. Es una forma simple de gestión de migraciones sin herramientas externas.
05

Gestión de Ingredientes (CRUD via AJAX)

Todas las operaciones de creación, edición y desactivación de ingredientes se procesan en el mismo archivo inventario.php. Cuando llega una petición POST, el servidor detecta que es una llamada AJAX y responde en JSON; cuando llega una petición GET, renderiza el HTML completo. Este patrón se conoce como endpoint dual. 

// Detección de petición AJAX en inventario.php
if($_SERVER['REQUEST_METHOD'] === 'POST') {
    header('Content-Type: application/json');
    $d = json_decode(file_get_contents('php://input'), true);
    $accion = $d['accion'] ?? '';
    try {
        if($accion === 'crear') { /* INSERT */ }
        elseif($accion === 'editar') { /* UPDATE */ }
        elseif($accion === 'movimiento') { /* ver sección 6 */ }
        elseif($accion === 'toggle_activo') { /* NOT activo */ }
    } catch(PDOException $e) {
        echo json_encode(['success'=>false, 'error'=>$e->getMessage()]);
    }
    exit; // detener aquí para no renderizar HTML
}

Los prepared statements de PDO son obligatorios en toda operación de escritura. Vinculan los parámetros por separado de la consulta SQL, eliminando la posibilidad de inyección SQL:

// Prepared statement — los valores se envían separados del SQL
$conn->prepare("INSERT INTO ingredientes
    (nombre, categoria, unidad, stock_actual, stock_minimo, costo_unitario)
    VALUES (?, ?, ?, ?, ?, ?)")
     ->execute([$d['nombre'], $d['categoria'], $d['unidad'],
                $d['stock_actual'], $d['stock_minimo'], $d['costo_unitario']]);
06

Sistema de Movimientos de Stock

Cada cambio en el stock de un ingrediente se registra como un movimiento, nunca se modifica el stock directamente sin traza. Esto garantiza trazabilidad total: siempre se puede ver qué pasó, cuándo y quién lo hizo.

El sistema soporta tres tipos de movimiento:

TipoFórmulaValidaciónCaso de uso
entrada stock_despues = antes + cantidad Ninguna — siempre válido Recepción de mercadería, compra de insumos
salida stock_despues = antes − cantidad Se requiere cantidad ≤ stock_actual Retiro manual de inventario, merma
ajuste stock_despues = cantidad (valor absoluto) Ninguna — reemplaza el valor Corrección tras conteo físico de inventario 
$antes = (float)$ing['stock_actual'];
$cant  = (float)$d['cantidad'];

if($d['tipo'] === 'entrada') {
    $despues = $antes + $cant;

} elseif($d['tipo'] === 'salida') {
    if($cant > $antes) {
        echo json_encode(['success'=>false,
            'error'=>'Stock insuficiente (disponible: '.$antes.')']);
        exit;
    }
    $despues = $antes - $cant;

} else { // ajuste: el usuario define el stock final
    $despues = $cant;
    $cant = round(abs($despues - $antes), 2); // diferencia para el log
}

// Actualizar stock e insertar registro de movimiento
$conn->prepare("UPDATE ingredientes SET stock_actual=? WHERE id=?")
     ->execute([$despues, $d['id']]);

$conn->prepare("INSERT INTO movimientos_inventario
    (ingrediente_id, tipo, cantidad, stock_antes, stock_despues, nota, usuario_id)
    VALUES (?, ?, ?, ?, ?, ?, ?)")
     ->execute([$d['id'], $d['tipo'], $cant, $antes, $despues,
                $d['nota'] ?? null, $_SESSION['usuario_id']]);
07

Sistema de Recetas

La tabla recetas es el puente entre el módulo de ventas y el de inventario. Cada fila representa "un producto requiere X unidades de un ingrediente". Un producto puede tener múltiples ingredientes y un ingrediente puede aparecer en múltiples recetas.

La restricción UNIQUE KEY uk_prod_ing (producto_id, ingrediente_id) previene duplicados a nivel de base de datos: MySQL rechazará cualquier intento de insertar el mismo ingrediente dos veces para el mismo producto, independientemente de la lógica de la aplicación.

La gestión de recetas se realiza desde erp/productos.php. El frontend carga la receta actual vía AJAX (accion: 'receta_get'), permite al usuario agregar o quitar ingredientes, y al guardar reemplaza toda la receta con una operación DELETE + INSERT múltiple: 

elseif($accion === 'receta_guardar') {
    // Eliminar receta anterior completa
    $conn->prepare("DELETE FROM recetas WHERE producto_id=?")
         ->execute([(int)$d['producto_id']]);

    // Insertar la nueva receta línea por línea
    $ins = $conn->prepare(
        "INSERT INTO recetas (producto_id, ingrediente_id, cantidad) VALUES (?,?,?)");

    foreach($d['ingredientes'] ?? [] as $ing) {
        if((float)$ing['cantidad'] > 0 && (int)$ing['ingrediente_id'] > 0) {
            $ins->execute([
                (int)$d['producto_id'],
                (int)$ing['ingrediente_id'],
                (float)$ing['cantidad']
            ]);
        }
    }
    echo json_encode(['success'=>true]);
}
Reutilización del prepared statement El objeto $ins se prepara una sola vez y se ejecuta múltiples veces dentro del foreach. Esto es más eficiente que preparar dentro del loop: MySQL parsea y compila el SQL una sola vez, y en cada iteración solo recibe los valores.

El archivo descontar_ingredientes_fn.php implementa la función descontarIngredientes($conn, $orden_id), que se invoca automáticamente cuando una orden alcanza el estado 'completado'. Esta función resuelve el problema de vincular el stock físico con el flujo de ventas sin intervención manual.

Un aspecto crítico de la función es el patrón de idempotencia: la columna ingredientes_descontados actúa como flag que previene un doble descuento. Si por alguna razón la función se llama dos veces sobre la misma orden (por ejemplo, si el usuario recarga la página), el descuento solo ocurre una vez. 

function descontarIngredientes($conn, $orden_id) {
    setupRecetasTables($conn); // crear tablas si no existen

    // ── Patrón idempotente: verificar flag antes de proceder ──
    $chk = $conn->prepare(
        "SELECT ingredientes_descontados FROM ordenes WHERE id=?");
    $chk->execute([$orden_id]);
    $ord = $chk->fetch(PDO::FETCH_ASSOC);
    if(!$ord || $ord['ingredientes_descontados']) return; // ya descontado

    // ── Preparar statements FUERA del loop (eficiencia) ──
    $stmtProd   = $conn->prepare("SELECT id FROM productos WHERE nombre=? LIMIT 1");
    $stmtRec    = $conn->prepare("SELECT ingrediente_id, cantidad FROM recetas WHERE producto_id=?");
    $stmtStock  = $conn->prepare("SELECT stock_actual FROM ingredientes WHERE id=? AND activo=1");
    $stmtUpdate = $conn->prepare("UPDATE ingredientes SET stock_actual=? WHERE id=?");
    $stmtLog    = $conn->prepare("INSERT INTO movimientos_inventario
        (ingrediente_id, tipo, cantidad, stock_antes, stock_despues, nota)
        VALUES (?, ?, ?, ?, ?, ?)");

    // ── Procesar cada ítem de la orden ──
    foreach($detalles as $item) {
        $stmtProd->execute([$item['producto_nombre']]);
        $prod = $stmtProd->fetch(PDO::FETCH_ASSOC);
        if(!$prod) continue; // producto sin receta → omitir

        $stmtRec->execute([$prod['id']]);
        $receta = $stmtRec->fetchAll(PDO::FETCH_ASSOC);

        foreach($receta as $r) {
            $total = round($r['cantidad'] * $item['cantidad'], 4);
            $antes   = (float)$ingRow['stock_actual'];
            $despues = round(max(0, $antes - $total), 4); // no puede ser negativo
            $stmtUpdate->execute([$despues, $r['ingrediente_id']]);
            $stmtLog->execute([...]);
        }
    }
    // ── Marcar orden como procesada (idempotencia) ──
    $conn->prepare(
        "UPDATE ordenes SET ingredientes_descontados=1 WHERE id=?")->execute([$orden_id]);
}
Decisión de diseño crítica En detalle_orden, la columna producto_id puede ser NULL (una orden puede crearse sin productos). Por esto, la función no hace JOIN por ID sino que busca el producto por nombre (WHERE nombre=?). Esto hace que el sistema sea robusto a datos incompletos.

Integración con el Punto de Venta

La función descontarIngredientes() se invoca en dos puntos del flujo de ventas, cubriendo ambas rutas por las que una orden puede cerrarse:

ArchivoCuándo se llamaPosición en el flujo
completar_orden.php Cuando el camarero cierra la orden manualmente Después del UPDATE estado='completado', dentro de try/catch
procesar_pago.php Cuando el pago cubre el total de la orden Después del $conn->commit(), solo si $pendiente <= 0

En ambos casos, la llamada está envuelta en try/catch vacío para que un posible fallo en el descuento de inventario no revierta ni bloquee el cierre de la orden — el pago ya fue registrado y la transacción ya fue confirmada. 

// En completar_orden.php
$stmt = $conn->prepare("UPDATE ordenes SET estado='completado' WHERE id=?");
$stmt->execute([$orden_id]);

try { descontarIngredientes($conn, $orden_id); } catch(Exception $e) {}

// En procesar_pago.php — después del commit de la transacción de pago
$conn->commit();
if($pendiente <= 0) {
    try { descontarIngredientes($conn, $orden_id); } catch(Exception $e) {}
}
